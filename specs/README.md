# SDD-спецификации поведения AI-buddy

Формат — [OpenSpec](https://github.com/Fission-AI/OpenSpec): одна папка на возможность (capability), в ней `spec.md` с требованиями (`### Requirement`) и сценариями (`#### Scenario`) в форме GIVEN / WHEN / THEN.

Разработка агента шла от спецификации: сначала спека, затем код и сценарные тесты по её критериям приёмки.

| Спека | О чём |
|---|---|
| [00-permissions-and-guard](00-permissions-and-guard/spec.md) | права, подтверждение действий, отказы, защита, сбои |
| [01-leave-request](01-leave-request/spec.md) | оформить отгул |
| [02-onboarding-next-steps](02-onboarding-next-steps/spec.md) | что делать дальше по адаптации |
| [03-team-knowledge-qa](03-team-knowledge-qa/spec.md) | вопросы о команде и инструментах |
| [04-access-requests](04-access-requests/spec.md) | доступы и согласование руководителем |

## Как проверяются критерии

У каждого сценария есть идентификатор `AC-NN-M`. Его проверяет автотест с тем же идентификатором в имени или комментарии:

```bash
grep -rn "AC-01-3" agent/        # найти тест критерия
cd agent && make test            # прогнать все
```

Сценарные тесты (`agent/internal/scenario/`) поднимают полную цепочку `agent → MCP (Streamable HTTP) → API` в одном процессе с детерминированным LLM (`LLM_PROVIDER=mock`) и имитацией API Бэкенда 1. Те же сценарии с реальной LLM проверяет eval-набор [`evals/`](../evals/README.md).

## Общие определения

- **Пользователь** — владелец JWT. Тестовые: Анна и Борис (стажёры, команда «Доставка», наставник Дмитрий, руководитель Елена), Вера (стажёр, «Фронтенд Объявлений», руководитель Фёдор).
- **Чтение** — инструмент с `readOnlyHint=true`, выполняется сразу.
- **Действие** — инструмент, меняющий данные. Выполняется только по цепочке `action_proposal` → `confirm`.
- **Карточка** — событие `action_proposal` и pending-действие в Redis (TTL 30 минут).
- Все инструкции базы знаний — тестовые; агент говорит «по тестовой инструкции».
